## 1. [measure]

```python
import keras
import numpy as np

x = np.linspace(-1, 1, 64, dtype="float32").reshape(-1, 1)
for batch_size in (16, 64):
    keras.utils.set_random_seed(0)
    model = keras.Sequential([keras.Input((1,)), keras.layers.Dense(1)])
    model.compile(optimizer=keras.optimizers.Adam(0.1), loss="mse")
    model.fit(x, 2 * x + 1, epochs=100, batch_size=batch_size, verbose=0)
    print(batch_size, int(model.optimizer.iterations.numpy()))
```

```text
16 400
64 100
```

One epoch has `ceil(64 / batch_size)` steps. With batch size 16 that is 4 steps, so 100 epochs give 400 updates. With batch size 64 an epoch is one step, so 100 epochs give 100 updates. The number of updates changes with the batch size even when the number of epochs does not.

## 2. [break]

```python
import keras
import numpy as np

x = 20 * np.linspace(-1, 1, 64, dtype="float32").reshape(-1, 1)
y = 2 * x + 1
for scale, data in (("x in [-1, 1]", x / 20), ("x in [-20, 20]", x)):
    keras.utils.set_random_seed(0)
    model = keras.Sequential([keras.Input((1,)), keras.layers.Dense(1)])
    model.compile(optimizer=keras.optimizers.SGD(0.1), loss="mse")
    history = model.fit(data, 2 * data + 1, epochs=100, batch_size=16, verbose=0)
    print(f"{scale:16s} final loss {history.history['loss'][-1]:.3g}")
```

```text
x in [-1, 1]     final loss 1.31e-13
x in [-20, 20]   final loss nan
```

The gradient of the mean squared error with respect to the weight contains the factor `x * x`. When `x` is 20 times larger, the gradient is about 400 times larger. A step that was stable at a gradient of size 1 now overshoots by a factor that grows with each update. The stable learning rate depends on the scale of the input. This is the reason that the data must be normalized before training ([Chapter 5](../../chapters/05-data-pipelines.md)).

## 3. [judge]

**Position:** reject the rule. A small loss on the training data does not make a model good, and 100 epochs is not a property of the problem.

**What a good answer weighs.** The loss on the training data says that the model fits the data it saw. It says nothing about data it did not see ([Chapter 8](../../chapters/08-overfitting-and-regularization.md)). The chapter also shows two runs that finish without an error and give a bad result: a loss of `nan` and a loss of 1.27. A fixed epoch count would ship both. Training is finished when a measurement on held-out data stops improving, so the rule must name that measurement and not a number of epochs.

**Strongest objection.** A fixed recipe is easy to audit, and a team that uses one recipe on every problem makes fewer mistakes than a team that tunes each run. This is true when the recipe also contains a check. The rule fails because it has no check, not because it is fixed.

**What would overturn it.** A set of past projects in which a fixed-epoch recipe, with a held-out check added, gave the same result as early stopping at lower cost.
