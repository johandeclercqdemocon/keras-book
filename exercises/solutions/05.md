## 1. [measure]

```python
import math

from examples.digits import load

x_train, _, y_train, _ = load()
n = len(x_train)
for batch_size in (32, 64, 100):
    batches = math.ceil(n / batch_size)
    last = n - (batches - 1) * batch_size
    print(f"batch size {batch_size:3d}: {batches} batches, last batch {last} images")
```

```text
batch size  32: 43 batches, last batch 3 images
batch size  64: 22 batches, last batch 3 images
batch size 100: 14 batches, last batch 47 images
```

The number of batches is `ceil(1347 / batch_size)`. The last batch holds the remainder. A batch of 3 images gives a noisy gradient. If this matters, pass `drop_remainder=True` to `tf.data` or make `__len__` of the `PyDataset` use the floor.

## 2. [break]

```python
import numpy as np
from keras import layers, ops
from examples.digits import load

x_train, x_test, _, _ = load(scale=False)
norm = layers.Normalization()
norm.adapt(x_train)

patched = x_test.copy()
patched[:, 24] = 0.0
print("original test images, largest output:", float(np.abs(ops.convert_to_numpy(norm(x_test))).max()))
print("pixel 24 set to zero, largest output: ", round(float(np.abs(ops.convert_to_numpy(norm(patched))).max()), 1))
```

```text
original test images, largest output: 10000000.0
pixel 24 set to zero, largest output:  88.6
```

The huge value disappears because the data no longer contain it. The fix removes the evidence and keeps the cause. In production a pixel that was constant in training and is not constant now says that the input has changed: a new sensor, a new scanner, a new crop. A silent patch hides that message. The better fix is a check at the input that raises or logs when a feature leaves the range seen in training.

## 3. [judge]

**Position:** do not celebrate yet. A validation accuracy of 99% on a new data set is a reason to look for a fault first.

**What a good answer weighs.** The chapter shows that `validation_split` takes the last 20% of the rows. If the database query returns rows sorted by time, by customer or by label, the validation set is a different population from the training set, and the score can be too low or too high. A score that is too high has other causes, and the questions are the same ones that the chapter measures. Do rows of one customer appear in both parts? Did a statistic such as a mean come from all the rows? Does a feature encode the answer, such as an identifier or a time stamp? Ask for a stratified or grouped split with a seed and for the accuracy of a trivial baseline, such as the most common class.

**Strongest objection.** Sometimes the task is easy and 99% is correct. This is true. The remedy is to check, not to assume either way.

**What would overturn it.** The same score on a second split that groups the rows by the unit that must generalize, and a baseline that scores far lower.
